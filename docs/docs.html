docs / setup

Setup

Four tools, one install command.

1. Prerequisites

ToolWhy
uv + Python 3.11+Runs every script — each carries PEP 723 inline deps, no project setup needed.
git + gh (authenticated)Planner/implementer read the issue via gh; the engine worktrees the target repo.
piThe RPC harness that drives each model — must have your providers configured.
tmuxHosts the long-running phase jobs in parallel.
# verify everything in one go
gh auth status && pi --version && git status && tmux -V && uv --version

2. Install the skill

It is fully self-contained — engine, scripts, prompts, and configs all live inside the skill directory:

npx skills add alejandro-ao/duobench

Working on duobench itself? Clone the repo and uv sync — the skill lives at skills/duobench/ and .claude/skills symlinks to it.

3. Sanity-check your models

Every model key you plan to use must resolve in the skill's config/models.yaml and its provider/model_id must be registered + authenticated in Pi. The agent checks this in preflight before spending money.

docs / usage

Usage

The intended way to run duobench is to ask the agent — see the examples on the home page. The agent will: confirm the issue + model matrix + estimated job count, announce the output dir (default ./duobench-runs/<timestamp>/), launch plan → implement → judge phase jobs in tmux (gating each phase on completion), aggregate, then write and run a seaborn plotting script and show you the charts.

Watch any job live

tmux ls                                  # list duobench jobs
tmux attach -t <job>                     # watch one (detach with Ctrl-b then d)
tail -f <run-dir>/conditions/<cond>/trial-0/job.log

Or call the scripts directly (no agent)

Run them from a clone of the target repo (the engine worktrees the current directory):

SKILL_DIR=<path to the installed skill>   # in this repo: $PWD/skills/duobench
RUNS=$PWD/duobench-runs
TS=$(date -u +%Y-%m-%dT%H-%M-%S); ISSUE=https://github.com/org/repo/issues/123

# 1) plan (one per unique planner)
uv run "$SKILL_DIR/scripts/run_phase.py" --phase plan \
  --run-dir $RUNS/$TS --out-dir $RUNS/$TS/shared-plans/kimi-k2.6/trial-0 \
  --issue $ISSUE --planner kimi-k2.6 --trial 0

# 2) implement (one per condition) — points at that planner's plan.md
uv run "$SKILL_DIR/scripts/run_phase.py" --phase implement \
  --run-dir $RUNS/$TS --out-dir $RUNS/$TS/conditions/kimi-k2.6-solo/trial-0 \
  --issue $ISSUE --condition kimi-k2.6-solo \
  --planner kimi-k2.6 --implementer kimi-k2.6 \
  --plan-path $RUNS/$TS/shared-plans/kimi-k2.6/trial-0/plan.md --trial 0

# 3) judge (one per condition × judge) — commit SHA from the implement result.json
uv run "$SKILL_DIR/scripts/run_phase.py" --phase judge \
  --run-dir $RUNS/$TS --out-dir $RUNS/$TS/conditions/kimi-k2.6-solo/trial-0 \
  --issue $ISSUE --condition kimi-k2.6-solo --judge-key gpt-5.5 \
  --build-dir $RUNS/$TS/conditions/kimi-k2.6-solo/trial-0/worktree \
  --commit-sha <SHA> --trial 0

# 4) aggregate → results.json   5) plot → results/*.png
uv run "$SKILL_DIR/scripts/aggregate.py" $RUNS/$TS
uv run "$SKILL_DIR/scripts/plots_example.py" $RUNS/$TS

Benchmarking an issue from another repo (SWE-bench style)

The implementer commits into a worktree of the current directory, so to benchmark an issue from a different repo, run phase jobs from a clone of that repo, checked out at the pre-fix base (first parent of the fixing PR's merge commit):

TGT=~/repos/duobench-targets/flask-4041
BASE=$(gh api repos/pallets/flask/commits/<merge_sha> -q '.parents[0].sha')
git clone https://github.com/pallets/flask.git "$TGT" && git -C "$TGT" checkout "$BASE"
git -C "$TGT" config extensions.worktreeConfig true  # REQUIRED, else implement jobs fail
cd "$TGT"   # then launch phase jobs from here
One issue is an anecdote. Multi-issue / multi-trial sweeps make results statistically meaningful but cost scales as issues × conditions × jobs × trials — they are opt-in only. Start small: one condition, one trial, a test issue.
docs / mechanics

How the skill works

The SKILL.md is an orchestration contract for the agent. A condition is one planner×implementer pairing, identified as <planner>-x-<implementer> (or <planner>-solo when they're equal). Each phase is one Pi RPC instance run by scripts/run_phase.py, which writes a result.json sentinel as its last action — the agent polls for that file to know a job is done.

Phases

PhaseJobsReadsWrites
planone per unique planner × trialthe issue + reposhared-plans/<planner>/trial-<n>/plan.md
implementone per condition × trialthe planner's plan.mdworktree/, commit.json, verify.json, trial.json
judgeone per condition × judge × trialthe commit + diffjudge-transcripts/<judge>.json
aggregateone (pure, no model calls)every trial.jsonresults.json
plotone (pure)results.json + trial.jsonresults/*.png + *.csv

The orchestration contract, in short

  • Strict order: plan → implement → judge → aggregate → plot. A phase never starts until every job of the previous phase has written its result.json.
  • One tmux job = one Pi instance = one unit of work. Money phases run in tmux with sessions named duobench__<TS>__<phase>__<unit>; pure steps run as plain background commands.
  • Confirm before spending. The agent shows the issue, condition list, judge panel, trials, output dir, and the job estimate (planners + conditions + conditions×judges, × trials) and waits for a go-ahead. opus+kimi with 2 judges and 1 trial = 14 model-calling jobs.
  • Concurrency cap: 2 money-jobs at once by default.
  • run_state.json is the source of truth — a fresh agent can resume any run from disk + tmux ls, never from memory.
  • Idempotent + resumable: a unit whose out-dir already has a result.json with status:"complete" is skipped; adding a condition reuses existing plans and re-aggregates the whole run dir.

What each agent role is asked to do

  • Planner — inspect the issue (gh) and repo; produce a plan; never modify files.
  • Implementer — work in an isolated git worktree, run checks, create one local commit, return its SHA. Never push, never open a PR. Enforced three ways: the prompt, PATH-prepended git/gh wrappers that reject pushes/PRs, and removal of the upstream remote.
  • Judge — inspect the commit/diff/worktree read-only and emit strict JSON scores on task_completion, correctness, code_quality, verification (1–10). cost_efficiency = quality ÷ cost, computed by aggregate.py, not judged.

Models & costs

--planner, --implementer, and --judge-key accept a registry key from config/models.yaml (kimi-k2.6, gpt-5.5) or a raw Pi spec (openai-codex/gpt-5.5), optionally with a :thinking suffix. Cost prefers Pi-reported billing; otherwise it falls back to the model's pricing block ($/MTok).

Set cache_read for any configured-priced model. An agentic implement loop is ~90% cache-read tokens; without a cache_read rate those hits are billed at full input price, inflating cost several-fold and making efficiency comparisons unfair.
# config/models.yaml
models:
  kimi-k2.6:
    provider: kimi-coding
    model_id: kimi-for-coding
    thinking: high
    pricing: { input: 0.95, output: 4.00, cache_read: 0.16 }
judges: [kimi-k2.6, gpt-5.5]
docs / scripts

Scripts reference

Everything lives under skills/duobench/scripts/. Each script carries PEP 723 inline dependencies, so uv run <script> works with no project setup.

run_phase.py — the phase runner

Runs exactly one unit of work (one Pi RPC instance) for one phase, then atomically writes a result.json sentinel into --out-dir. The agent (or you) launches one of these per plan/implement/judge job.

FlagPhasesDescription
--phase plan|implement|judgeallwhich phase to run
--run-dir / --out-dirallrun root, and this job's output dir (where result.json lands)
--issue URLallGitHub issue (required)
--trial Nalltrial index
--timeout SECallwall-clock (defaults: plan 600, implement 1800, judge 300)
--submission-mode local_commit|primplementdefault local_commit (safe); pr is the legacy PR-creating flow
--planner SPECplan, implementplanner model spec/key
--implementer SPEC / --plan-pathimplementimplementer spec; path to the planner's plan.md
--judge-key SPEC / --build-dir / --commit-shajudgejudge spec; the trial's worktree; the commit to score
--models-config / --conditions-config / --costs-configallconfig paths
--no-pi-sessionsalldon't persist Pi sessions

aggregate.py — fold trials into results.json

uv run "$SKILL_DIR/scripts/aggregate.py" runs/<ts> [--judges kimi-k2.6,gpt-5.5]

Pure — no model calls. Run it after all judge jobs finish (and again after adding a condition). It folds every conditions/*/trial-*/trial.json into the judged record, writes judge_scores back into each trial.json, (over)writes results.json, and prints a leaderboard. Safe to re-run: it rescans the whole run dir, so old + newly added conditions merge automatically.

plots_example.py — the standard chart set

uv run "$SKILL_DIR/scripts/plots_example.py" runs/<ts>

Writes results/*.png (+ matching .csv), all styled consistently: leaderboard, cost-vs-quality (with iso-efficiency guide lines), dimensions, self-bias (own-vs-other judge bars), and cost-breakdown (plan vs implement spend). To customize a run's charts, copy it to <run-dir>/plots.py and adapt — see references/plotting.md.

plot_styles.py — shared theme + data loaders

Imported by plotting scripts; not run directly. Provides apply_duobench_theme(), tidy pandas loaders (load_results, load_trials), per-model stable colors (color_for), and dynamic dimension-name discovery so charts stay consistent across runs and schema drift.

export_session.py — transcripts to Markdown

uv run "$SKILL_DIR/scripts/export_session.py" <session.jsonl> <out.md>

Renders a session .jsonl transcript into readable Markdown: user prompts, assistant text, tool calls, and truncated tool results. Handy for inspecting what a planner, implementer, or judge actually did.

docs / output

Output layout

Each run writes everything under its run dir (default ./duobench-runs/<timestamp>/):

run_state.json                       # orchestration state (agent-owned; enables resume)
results.json                         # aggregated leaderboard + self-bias
results/                             # the charts + csvs
  leaderboard.png / .csv
  cost-vs-quality.png / .csv
  dimensions.png / .csv
  self-bias.png / .csv
  cost-breakdown.png / .csv
plots.py                             # the run's plotting script (if customized)
shared-plans/<planner>/trial-<n>/
  plan.md  shared-plan.json  planner-transcript.json  result.json
conditions/<cond-id>/trial-<n>/
  worktree/                          # isolated git worktree for the candidate fix
  .duobench-harness/                 # safety shims/hooks kept outside the candidate fix
  plan.md  commit.json  verify.json  trial.json
  implementer-transcript.json
  judge-transcripts/<judge>.json
  result.json                        # implement-job sentinel
  results/judge-<judge>.json         # per-judge-job sentinel

trial.json is self-contained (benchmark, artifacts, record, judge_scores), so aggregate.py and any plotting script can consume a run without re-running it. The plots are a decision aid — inspecting the actual worktree commits is the last step before trusting a pairing on a real project.

Troubleshooting

ProblemSolution
--issue is requiredPass --issue https://github.com/org/repo/issues/123.
gh CLI is requiredgh auth login && gh auth status.
Pi cannot find a modelCheck provider/model_id in config/models.yaml match your Pi install.
A job seems stucktmux attach -t <job> and tail -f <out>/job.log; its result.json appears when done.
Implement jobs error with --worktree cannot be used with multiple working treesgit -C <repo> config extensions.worktreeConfig true, then retry.
A model looks far more expensive than expectedIt's configured-priced without a cache_read rate — add one to models.yaml.
